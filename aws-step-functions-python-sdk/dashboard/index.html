Wherobots Jobs from Step Functions

Submit a Sedona job to Wherobots Cloud from a Step Functions pipeline, let the job report its own success or failure over a task-token callback, and let heartbeats plus a reusable poller catch everything the job can't report — a driver OOM included.

01

How the pieces fit

The pipeline pauses on a task token. The callback path is the happy path: the job itself posts success or failure through API Gateway, and the state machine wakes instantly. The fallback path exists for deaths the job cannot report — heartbeats stop, the timeout fires, and the reusable poller asks Wherobots what really happened.

callback path (happy) fallback path (hard death) submit failure callback → JobFailed with the job's traceback as cause
02

Upload the job to Wherobots

The wherobots-python-sdk FilesAPI fetches short-lived STS credentials from the Wherobots API and uploads the job script; the resulting s3:// URI is what the pipeline submits.

    03

    Build the AWS infrastructure

    Plain AWS CLI calls, each echoed before it runs: two IAM roles, four Lambdas (submit, check-status, callback relay + its API Gateway endpoint, find-run) and the two state machines. Safe to re-run — existing resources are updated, never duplicated.

      04

      Run the pipeline

      Submit + await hands the job a task token and pauses; the job reports back itself. The fallback lanes stay empty on a healthy run — they light up only when heartbeats stop. Tick the checkbox to make the job throw on purpose and watch the failure callback carry the real traceback into the execution as its cause.

      submit + await callback find run (fallback) poll (fallback) next step failed ┆ red dashed rule = heartbeat timeout detected one block = 10 s · the pulsing block is the current one
        05

        Teardown

        Deletes the API Gateway endpoint, all four Lambdas, both state machines and both IAM roles — only resources named with your RESOURCE_PREFIX. The job script in Wherobots storage is left untouched.
